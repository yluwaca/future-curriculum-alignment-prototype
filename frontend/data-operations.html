System Documentation

Chapter 4 working notes: portal purpose, model workflow, indicator interpretation, and validation process

1. Purpose of the FUTURE/PCLMAS portal

FUTURE/PCLMAS is a curriculum-labour-market alignment artefact. Its purpose is to bring curriculum evidence, labour-market evidence, skill taxonomy evidence, forecast signals, and human review into one governed decision-support environment. The portal does not replace curriculum committees; it prepares evidence so that curriculum administrators, analysts, academics, and governance reviewers can make better-informed decisions.

The cleaned portal separates decision-facing views from operational and technical workspaces. Executive and curriculum users see evidence, readiness, recommendations, and decisions. Admin, analyst, and data-scientist users have access to ingestion, labelling, model training, source monitoring, and system operations according to RBAC.

3. Executive Dashboard interpretation

The Executive Dashboard is the landing view for senior curriculum stakeholders. It summarises whether the system has enough evidence and processing output to support defensible recommendations. It should be interpreted as a readiness and decision-output page, not as a raw data-entry or technical troubleshooting page.

  • Curriculum Records counts uploaded curriculum documents and imported programme/module records.
  • Skills Mapped counts evidence mappings created after curriculum or labour-market text has been linked to canonical skills.
  • Average Alignment summarises generated alignment scores after processing has run.
  • Pending Reviews counts recommendations that require human decision-making.
  • Recommendation Priorities shows the executive action queue once recommendations exist.
  • Pipeline Health separates data readiness from model output readiness, including ingestion jobs, labour facts, canonical signals, vector backend readiness, recommendations, and analytics records.
  • Recommendation Dossier provides traceability for a selected recommendation: evidence, forecast context, explanation, and decision history.

4. Evidence flow from upload to decision

The system follows a staged evidence pipeline. Source data is first uploaded or imported. It is then normalised into a common repository, linked to canonical skills, processed into alignment and forecast outputs, and finally converted into recommendations that require human review.

5. Alignment labelling and supervised model validation

Alignment labelling is the human-supervised step required before the XGBoost alignment model can be trained honestly. Reviewers compare curriculum evidence against labour-market evidence and assign a 1–5 alignment label. These labels must be independent of model predictions; generated model scores are not shown to reviewers and must not be used as labels.

The labelling process is deliberately governed. A first reviewer labels a task, a second reviewer independently labels the same task, and disagreements require adjudication. Completed labels are locked into an immutable reviewed-label dataset. That locked dataset becomes the training and test evidence for supervised alignment modelling.

LabelMeaningInterpretation
1No alignmentThe curriculum evidence does not cover the labour-market signal.
2Weak alignmentThe evidence is only indirectly related or too general.
3Moderate alignmentSome relevant concepts are present, but coverage is partial.
4Strong alignmentThe curriculum clearly covers the skill area in meaningful detail.
5Very strong alignmentThe curriculum explicitly and deeply covers the skill, including applied competence.

6. Forecasting and LSTM readiness

The forecasting component estimates future skill-demand direction from time-indexed evidence. Transparent baseline forecasts can run from current canonical signals, while the LSTM model requires longer historical sequences. A small time series can prove that the pipeline works, but it should not be over-interpreted as strong predictive evidence.

Data depthUsefulnessInterpretation
30–60 sequence rowsPrototype runConfirms the training code executes; weak evidence for prediction.
100–200 sequence rowsUseful DEV evaluationAllows basic walk-forward validation and baseline comparison.
300–500+ sequence rowsBetter research evaluationSupports more meaningful comparisons across skills and time windows.
1,000+ observationsProduction-style evaluationBetter for stable forecasting, subgroup checks, and model governance.

Recommended sources for time-indexed demand evidence include StatsSA QLFS across as many quarters/years as possible, CHE VitalStats for higher-education context, approved public job-posting exports with dates, and documented public proxy datasets where licensing permits use.

7. Vector backend and semantic matching

Semantic matching uses pgvector in PostgreSQL so that related concepts can be compared even when the exact wording differs. A healthy state appears as Vector Backend = pgvector with a ready badge. If pgvector is not available in a deployment environment, the system should report the backend as not ready rather than hiding the issue behind a fallback.

8. Practical instructions

This System Documentation page explains the model, portal areas, and research-facing interpretation. The operational sequence is: import official curriculum documents in Curriculum Documents, confirm the derived Subject Profile Validation records, import and normalise labour-market sources, generate evidence mappings, validate curriculum evidence, generate independent alignment-labelling tasks, lock the reviewed label dataset, then train/evaluate candidate models.

Subject Profile Validation is the reporting clean-up step after upload. The reviewer confirms the institution, faculty, department, programme or qualification name, programme code, qualification type, subject code, subject name, evidence year, NQF level, credits, purpose and prerequisites. The original uploaded document and extracted chunks remain preserved; only the structured profile used for dashboards, recommendations and reporting is corrected. Validated profiles leave the default work queue. Rejected profiles are kept for audit and can be viewed with the rejected/all filters, but they should not be treated as active curriculum evidence.

Curriculum Evidence Validation is the evidence-quality step. Reviewers inspect the extracted chunks shown in the validation window before approving a document version. If the text is unreadable, incomplete, from the wrong version, missing module/outcome evidence, or otherwise uncertain, the correct decision is Changes required or Rejected, with a short note describing what must be fixed.

Short expert notes are required because validation becomes part of the audit trail. If a reviewer agrees with the visible evidence, the note can be brief, for example: "Evidence reviewed and accepted; source, extraction, modules and outcomes are adequate for labelling." Step-by-step instructions are maintained in the Help Manual.
